# Experimental Zero lab controller

`cmd/xconnect-zero-lab` is a temporary integration fixture for an independent
One CLI and a real, freshly provisioned Xray/WireGuard gateway. It is **not the
production Zero API**. Production identity, leases, persistence, policy and
gateway snapshots belong in Accounts; the production UI belongs in Portal.
This command does not relocate those responsibilities into One.

The fixture follows `iac_modules/vpn-overlay/PRODUCTIZATION_DEVELOPMENT_PLAN.md`
for one-use invitation hashes, device-local WG private keys, Ed25519 client
configuration, VLESS/TLS/XUDP and ACKs. Reuse `iac_modules/vpn-overlay` deployment
and GitOps topology declarations. Do not create a parallel deployment stack or
store secrets in GitOps. The co-located privileged helper below is a deliberately
limited substitute for the plan's authenticated gateway agent and signed
snapshots; it is not an implementation of that production agent.

## Build and scope

From the independent XConnect-One repository:

```sh
go build -o dist/xconnect-zero-lab ./cmd/xconnect-zero-lab
go test -race ./internal/zerolab ./cmd/xconnect-zero-lab
go vet ./internal/zerolab ./cmd/xconnect-zero-lab
```

The controller builds on Linux and macOS, using Unix ownership checks and an
exclusive state-file lock. Actual gateway deployment targets Linux. Windows is
not supported by this experimental command. A Linux runner can cross-build it
with `GOOS=linux GOARCH=amd64 CGO_ENABLED=0`. Build the independent CLI separately
from `./cmd/xconnect`; install compatible external `xray`, `wg`, and `wg-quick`
executables and WireGuard kernel support as described in the repository README.

Supported scope is one network, one reserved device address, one gateway,
SignedConfig **v1**, invite join, durable device-session minting, config and ACK.
V2 requests fail with 406; do not pass `--signed-config-v2`. Accounts login,
production tenant authorization, policies, credential rotation/revocation,
portal, multi-device allocation, and gateway snapshot APIs are not provided.
The credential/enrollment scope arrays retain the existing wire contract, but
rotation and revoke endpoints are intentionally absent; a long-running
production lifecycle is not claimed. Session lifetime is 15 minutes, credential
lifetime 30 days, signed configuration lifetime one hour. Run a new disposable
lab before credential rotation is due. No automatic client refresh is installed.

## Secret sources and trust

The required `--admin-token-file`, `--signing-key-file`, and `--vless-id-file`
must be injected from Vault as owner-owned regular **0600** files:

| Vault field (pipeline agreement) | File contents | Purpose |
| --- | --- | --- |
| `ADMIN_TOKEN` | Random bootstrap bearer, at least 32 characters | Admin invite issuance only |
| `SIGNING_KEY` | Standard base64 of exactly 32 Ed25519 seed bytes | Signs lab configs |
| `VLESS_ID` | UUID provisioned in gateway Xray | Transport authentication |

The required runtime KV location is exactly `kv/data/sit/xconnect-one`.
Use the deployment's configured JWT role to access this path. No actual Vault provisioning is
performed by this binary. The pipeline must obtain these values with its
configured Vault JWT role and inject files over its authenticated deployment
channel. GitHub OIDC is a short-lived **CI identity**, separate from a VPS
runtime identity. Never install a GitHub OIDC token or pretend it is a perpetual
VPS credential. A continuously running Vault agent needs its own configured
runtime identity/role and renewal. For this disposable lab, protected file
injection at deploy time is sufficient; the controller does not retain a Vault
token or require background Vault login.

Generate ephemeral gateway WG keys on the gateway, with private key mode 0600.
The CLI generates its own WG private key locally. Neither private key is sent
to Zero. A disposable lab CA and server certificate may be generated by the
deployment, with CA/server private keys protected and only CA certificate copied
to the client. The certificate must contain the public controller IP/DNS SAN
and Xray's configured TLS server name. Install the CA certificate into the
client's OS trust store (used by both Go and Xray). `SSL_CERT_FILE` can select a
trusted CA bundle for Go, but environment propagation to Xray must also be
verified; OS trust installation is the deployment baseline. Never use
`InsecureSkipVerify`, Xray `allowInsecure`, `curl -k`, or disabled hostname checks.

Never log bootstrap tokens, invite URIs, credentials, signing seeds or Xray
configuration. Protected controller JSON includes a signed config with its
transport UUID; protect the entire state directory and backups as secrets.
Controller JSON stores only verifiers of invitations, enrollment sessions and
device credentials; signing seed and admin token remain in injected files.

## Listener and firewall

Prefer a private listen IP where possible. If `--listen :8443` is used on the
fresh gateway, configure **both cloud and host firewalls before starting it**:
allow TCP 8443 only from the designated CI runner and lab client addresses, and
TCP 22 only from the runner. Allow gateway TCP 443 only from the lab client.
Do not open the administrative listener to `0.0.0.0/0`. Admin and enrollment
share this HTTPS listener; the admin route additionally requires its bootstrap
bearer. Issue invites locally on the gateway over verified HTTPS and transfer
them to the client over the deployment's SSH channel. Never publish the admin
token as a URL, CLI argument, public artifact, GitOps field or public endpoint.

WG UDP 51820 is reached by gateway Xray at **127.0.0.1:51820**. It does not need
a public firewall rule. Bind the HTTP verification service only to the gateway
overlay IP; do not expose port 8080 publicly. `/healthz` is an unauthenticated
HTTPS readiness endpoint subject to the same network allowlist.

## Start and gateway integration

These paths are a deployment convention. All sensitive files must already
exist; the controller never synthesizes a gateway key, endpoint, address,
bootstrap bearer or transport UUID. Create `/var/lib/xconnect-zero-lab` mode
0700, owned by the process user. Inject secrets under `/opt/xconnect-lab` mode
0700. An actual command on the gateway is:

```sh
/usr/local/bin/xconnect-zero-lab \
  --listen :8443 --public-url "https://${GATEWAY_IP}:8443" \
  --state /var/lib/xconnect-zero-lab/state.json \
  --tls-cert /opt/xconnect-lab/server.crt \
  --tls-key /opt/xconnect-lab/server.key \
  --admin-token-file /opt/xconnect-lab/admin-token \
  --signing-key-file /opt/xconnect-lab/signing-key \
  --vless-id-file /opt/xconnect-lab/vless-id \
  --network-id net_lab --network-cidr 10.77.0.0/24 \
  --device-address 10.77.0.2/32 \
  --gateway-public-key "$ACTUAL_GATEWAY_WG_PUBLIC_KEY" \
  --gateway-host "$GATEWAY_IP" --gateway-port 443 \
  --gateway-server-name xconnect-lab.invalid \
  --peer-command /usr/local/libexec/xconnect-lab-peer
```

The deployment must allocate that network/address and supply the real gateway
IP and generated public key. `xconnect-lab.invalid` is a private lab certificate
SAN, not a public DNS dependency; connect to `--gateway-host` and verify this
SAN. `--public-url` is an HTTPS origin with no path, query, credentials or
fragment. These are flags, not environment-variable lookups by the binary.

Gateway Xray accepts VLESS over TLS/TCP on the supplied port, with the injected
UUID. Restrict its outbound routing to UDP **127.0.0.1:51820** and deny all other
destinations; this is a WG relay, not a general forward proxy. The gateway's WG
interface in this allocation uses `10.77.0.1/24` and listen port 51820. The
client's local Xray relay is `127.0.0.1:51830`; the signed WG peer endpoint is
that client loopback, while the signed transport remote is the actual gateway.
The controller reuses `overlay/signedconfig.Config.SigningBytes` and Compile,
including the fixed UDP relay target. Public WG endpoint fields must not be
substituted into that loopback contract.

`--peer-command` is an absolute executable path, invoked without a shell:

```text
/usr/local/libexec/xconnect-lab-peer DEVICE_WG_PUBLIC_KEY DEVICE_IPV4_PREFIX
```

The key is canonical base64 of 32 nonzero WG public-key bytes; the address is
the explicit configured IPv4 `/32`. The root-owned helper should independently
validate them and restrict the address to this lab's allocation. It applies:

```sh
wg set wg0 peer "$1" allowed-ips "$2"
```

Exit zero means the peer was installed, not merely queued. It must be
idempotent. Stdout/stderr are discarded; no secrets are passed to this helper.
The controller times it out after 15 seconds and returns 503 on failure.
The helper runs before a successful enrollment response and again before each
signed-config fetch, so syncing repairs a missing peer after interface setup.
The controller does not create the WG interface or start Xray; IaC deployment
does that. This lab uses co-location, not a remotely authenticated peer API.

## HTTP protocol and actual verification

All routes below are prefixed `/api/overlay/v1`:

| Method and route | Authorization | Contract |
| --- | --- | --- |
| POST `/join-tokens` | `Bearer` bootstrap token | Existing CreateJoinToken request/response |
| POST `/join-tokens/exchange` | One-use token in JSON | Existing exchange response including device credential and key ring |
| POST `/device/session` | `Device` durable credential | Nonce-bound 15-minute enrollment bearer |
| GET `/enrollment/signed-config` | Enrollment bearer | Bound device/network, Ed25519 v1 config |
| POST `/enrollment/signed-config/{generation}/ack` | Enrollment bearer | Exact device/config/generation ACK; duplicate receipt |
| GET `/signing-keys` | Bootstrap or enrollment bearer | Existing ETag/private cache contract |

Admin issuance request body is
`{"network_id":"net_lab","device_id":"dev_lab","platform":"linux","expires_in_seconds":900}`.
Consume `join_token.join_uri` privately. One active invite is supported; issuing
another before redemption replaces it. Invite creation is rejected after
enrollment or while a peer operation is pending. The CLI joins with:

```text
xconnect join --state-dir /var/lib/xconnect-one --device-id dev_lab --name lab-client <issued-invite-uri>
xconnect sync --state-dir /var/lib/xconnect-one
```

Run these privileged on the disposable Linux client. The CLI currently takes
the invite as an argument, so protect its short-lived process visibility and
disable shell tracing/history capture. Both join and sync start the tunnel;
there is no separate `up` needed. Verify a recent nonzero WireGuard handshake,
ping the actual gateway overlay address and read the run-specific HTTP marker
from `http://10.77.0.1:8080/`. Repeat HTTP after sync. After `xconnect down`,
that private service must be unreachable. Successful API ACK alone is not
proof of data-plane connectivity. No actual cloud/data-plane success is claimed
by the local HTTP integration tests.

## Persistence, failures and limitations

Writes use owner-only temporary files, fsync, atomic rename and directory
fsync. The process exclusively locks its state; a second process is refused.
Existing state and direct state-directory symlinks or permissive modes are
rejected. Topology, address, signing seed and transport credential are bound to
the saved state; changing them across restart is rejected. Admin token can be
replaced via injected file on restart. No key rotation/migration is implemented.

A durable pending binding is recorded before external peer installation.
Retries can only use the same device/platform/key. This prevents a crash from
silently reassigning the same address to another key. External WG state and
local JSON cannot form one transaction. A crash after helper success can leave
a peer installed; a lost successful enrollment response consumes the invite
without recovering the raw device credential. These exceptional cases require
operator teardown of this dedicated lab and recreation; never delete only the
controller state while leaving stale gateway peers. Persistence errors stop
subsequent API activity until restart. There is no production recovery workflow.

ACK records represent the client's reported application, not measured gateway
health. An unchanged config keeps its generation/ETag; near-expiry refresh
creates a new signed generation. At most 32 unexpired sessions are retained;
older sessions can be evicted. Only the current config/ACK is retained. No
multi-tenant audit, rate-limit service, revocation propagation or monitoring
is implemented. Restrict the experiment to fresh disposable resources.

Tests use the existing `overlay/controlplane.Client` against `httptest` HTTPS
with its CA explicitly trusted, verify and compile actual signatures, compare
the existing golden Ed25519 vector, reject an untrusted CA, replay and expired
session, check gateway failure and identity binding, and prove persisted
credential/session/config/ACK behavior across controller reconstruction.
